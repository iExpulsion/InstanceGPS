# Building InstanceGPS

The addon's Lua code works as-is. `InstanceGPS/Data.lua` (every instance's bosses, routes and hints) is generated by the scripts in `tools/`. You only need this page to change routes or rebuild that data. [ROUTES.md](ROUTES.md) explains how the routes are worked out.

## Layout

| Folder | What it is |
|---|---|
| `InstanceGPS/` | The addon itself. Point `Interface\AddOns\InstanceGPS` at it (a junction or symlink) to test changes in game. |
| `tools/` | The data build: `build.py` and its modules, `config.py` (hand-made route knowledge), `hints.json` (event hints), `boss_fixups.json` |
| `test/` | Lua test harness: a mocked 3.3.5 API (`wowmock.lua`) that loads the addon and walks its routes |
| `docs/` | This page and ROUTES.md |

These folders are created by the build and aren't tracked: `cache/`, `mmaps/`, `dbc/`, `dbc_stock/`, `blpcache/`, `out/`, `png/`, `dist/`.

## Setup

1. **Python 3** with Pillow, plus lupa for the tests:
   ```
   pip install pillow lupa
   ```
2. **A 3.3.5a client** (the one you play on, so its patches match), **[mpqcli](https://github.com/TheGrayDot/mpqcli)**, and an **[AzerothCore](https://github.com/azerothcore/azerothcore-wotlk)** checkout for its world SQL. Tell the tools where they are in `tools/paths_local.py` (not tracked) or with environment variables:
   ```python
   WOW_DIR = r"C:\Games\WoW 3.3.5a"
   MPQCLI = r"C:\Tools\mpqcli.exe"
   AC_WORLD_SQL = r"C:\azerothcore\data\sql\base\db_world"
   ```
3. **The navmesh**, in `mmaps/`. It's the same mmaps an AzerothCore server uses. With AzerothCore's Docker setup, copy it from the client-data volume (its name starts with your Compose project's name; `docker volume ls` shows it):
   ```
   docker run --rm -v azerothcore-wotlk_ac-client-data:/data -v "%CD%\mmaps:/out" alpine sh -c "cp /data/mmaps/* /out/"
   ```
4. **The client's DBCs** (from `tools/`). `dbc/` gets what the client actually loads, `dbc_stock/` Blizzard's own copies without add-on patches:
   ```
   python extract.py ../dbc AreaTable.dbc AreaTrigger.dbc DungeonEncounter.dbc DungeonMap.dbc DungeonMapChunk.dbc LFGDungeons.dbc Map.dbc TaxiPathNode.dbc WMOAreaTable.dbc WorldMapArea.dbc
   python extract_stock.py ../dbc_stock Achievement.dbc Achievement_Category.dbc Achievement_Criteria.dbc AreaTable.dbc DungeonEncounter.dbc DungeonMap.dbc DungeonMapChunk.dbc Map.dbc WMOAreaTable.dbc WorldMapArea.dbc
   ```

## Building (from `tools/`)

```
python build.py ../InstanceGPS/Data.lua --dbc ../dbc --cache ../cache                full build (~8 min the first time)
set DN_MAPS=43,209 & python build.py ../InstanceGPS/Data.lua --dbc ../dbc --cache ../cache   rebuild some instances, merged into the last full build
python build.py ../InstanceGPS/Data.lua --cache ../cache --write-only                rewrite Data.lua from the last build (seconds)
python render.py ../InstanceGPS/Data.lua ../png 43                                   draw an instance's routes over its in-game maps
```

The build prints a report. `NAV-BRIDGED` lines are straight hops where the navmesh has no connection (drops, doors, elevators); check them with `render.py` or in game. `/reload` picks up a new `Data.lua`.

Where to change things:

- **`tools/config.py`:** wings, boss order rules, teleporters and when they unlock, passages the navmesh lacks (`WALK_LINKS`), places a route must pass before a boss (`BOSS_VIA`), escorts whose path the route follows (`ESCORTS`), hard-mode variants and position overrides.
- **`tools/hints.json`:** event hints, each with its source in AzerothCore's scripts or database. A hint attaches to a boss, `after` a boss, or `any_order`.
- **`tools/boss_fixups.json`:** positions of summoned bosses and kill rules for multi-creature fights.
- **`tools/achstats.py`:** links between bosses and their kill statistics.

## Tests (from `test/`)

```
python run_test.py "" ui.lua         UI smoke test (also reset.lua, hard.lua, stats.lua, pathview.lua, idle.lua)
python suite.py [mapid ...]          walk every route for each faction and difficulty, and check the arrow
python hintcheck.py                  check every hint shows during the walks (needs a local build cache)
```

## Server Modules

InstanceGPS itself is built only from AzerothCore. A server's differences live in a module, an addon `InstanceGPS_<Server>` in a repo of its own, whose `Overrides.lua` calls `InstanceGPS:Override`. [MODULES.md](MODULES.md) has the format; anyone can write one without these tools, and the game applies it itself (`InstanceGPS/Override.lua`), with rough routes to moved and custom bosses.

**`python build.py --module <path> --dbc ../dbc --cache ../cache`** (from `tools/`; the path is the module's repo or addon folder) gives a module proper routes. It reads the same `Overrides.lua` (`tools/overlay.py`), routes every instance whose bosses it moves, adds or removes (plus its build-only `order`, `doors` and `links`), and writes the module's `Routes.lua`. In game those replace the AzerothCore instances whole, and the overrides apply on top. The base `Data.lua` isn't touched. A position from an override has no height (the game gives addons none), so the build takes the navmesh floor there on the map level given, nearest the boss's old height or the creatures around it.

`Routes.lua` records the InstanceGPS version and which version of each base instance it was built from; the module template's `tools/check.py` warns when the base has changed one of them since.

To test a module in game, point `Interface\AddOns\InstanceGPS_<Server>` at its folder (a junction, like the addon's).

## Releasing

1. Raise `## Version` in `InstanceGPS/InstanceGPS.toc` and push.
2. GitHub Actions runs the tests, builds `InstanceGPS-<version>.zip` and, because the version is new, publishes a release tagged `v<version>` with the zip attached. Pushes that don't change the version only build the zip as a workflow artifact.

`python tools/package.py` builds the same zip locally, in `dist/`. Server modules are released from their own repos.
